# MarkApiDown markdown convention

MarkApiDown is a markdown-native API spec system. A MarkApiDown project stores API documentation, executable requests, expected responses, pipelines, environment variables, and project configuration as markdown files. The same files are read by humans, the Rust engine, the web preview, CI, and AI coding agents.

This document is the canonical specification for the current MarkApiDown release. A developer who has never used MarkApiDown should be able to create a valid project from this document alone.

## Design goals

- Use markdown everywhere developers write or review API intent.
- Keep project configuration in `mad.md`, not a separate TOML, JSON, or YAML file.
- Make endpoint files executable without making them unreadable.
- Keep secrets out of versioned markdown.
- Make the browser preview and external editors work on the same files.
- Let AI agents author and execute specs using predictable structure.

## Project layout

A MarkApiDown project contains an `api-docs/` directory and a project-level `mad.md` file.

```text
api-docs/
├── README.md
├── mad.md
├── _shared/
│   ├── env.md
│   ├── auth.md
│   └── variables.md
├── apis/
│   └── <resource>/
│       └── <method>-<slug>.md
└── flows/
    └── <pipeline-name>.md
```

`api-docs/README.md` is generated by `mad index`. Do not edit it by hand.

`api-docs/mad.md` is the project configuration file. It is markdown with YAML frontmatter and structured YAML code blocks.

`api-docs/_shared/env.md` contains non-secret environment values such as base URLs. It must not contain tokens, passwords, private keys, or production credentials.

`api-docs/_shared/auth.md` contains reusable auth documentation and examples without real secrets.

`api-docs/_shared/variables.md` contains shared named variables that are safe to commit.

Each resource folder under `api-docs/apis/` contains endpoint files. The recommended filename format is `<method-lower>-<slug>.md`, for example `get-user-by-id.md`, `post-login.md`, or `delete-subscription-by-id.md`.

Pipeline files live in `api-docs/flows/` and describe multi-step flows.

## Project config: `mad.md`

Project-level config lives in `api-docs/mad.md`. It uses the same parser pattern as endpoint files: required YAML frontmatter, markdown sections, and structured YAML code blocks.

### Required frontmatter

```yaml
---
name: my-api
version: 1
default-env: dev
---
```

Fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `name` | yes | string | Project name shown in CLI, web preview, reports, and generated indexes. |
| `version` | yes | integer | MarkApiDown spec format version. For this spec format this must be `1`. |
| `default-env` | yes | string | Environment used when a command does not receive `--env`. |

Unknown frontmatter keys are warnings, not errors.

### Required sections

Sections should appear in this order.

````markdown
# My API

One-paragraph project description. This prose is read by humans and ignored by the parser.

## Defaults

```yaml
timeout: 5000
retry:
  attempts: 3
  backoff: exponential
auth: bearer
```

## Web preview

```yaml
port: 8080
host: 127.0.0.1
theme: auto
autosave: 2s
```

## Plugins

```yaml
plugins: []
```

## Notes

Free-form team notes, conventions, and gotchas. The parser ignores this section.
````

Sections are optional in the current release. If a section is missing, MarkApiDown uses built-in defaults. If a YAML code block contains an unknown key, MarkApiDown emits a warning and continues. This forward-compatible behavior allows future versions to add settings without breaking older clients.

`## Plugins` may contain an empty `plugins: []` block. the current MarkApiDown release does not execute plugins.

### Built-in defaults

If `## Defaults` is missing:

```yaml
timeout: 5000
retry:
  attempts: 0
  backoff: fixed
auth: none
```

If `## Web preview` is missing:

```yaml
port: 8080
host: 127.0.0.1
theme: auto
autosave: 2s
```

If `## Plugins` is missing:

```yaml
plugins: []
```

## Endpoint files

An endpoint file documents and executes one API endpoint.

### Endpoint frontmatter

Endpoint files must start with YAML frontmatter delimited by `---` at the beginning of the file.

```yaml
---
resource: users
protocol: http
method: GET
path: /users/:id
tags: [users, read]
version: 1
env: [dev, staging, prod]
auth: bearer
timeout: 5000
retry:
  attempts: 3
  backoff: exponential
---
```

Fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `resource` | yes | string | Resource folder and grouping name, for example `users` or `orders`. |
| `protocol` | yes | enum | `http`, `ws`, or `sse`. the current MarkApiDown release executes only `http`. |
| `method` | yes | enum | HTTP method such as `GET`, `POST`, `PUT`, `PATCH`, or `DELETE`. |
| `path` | yes | string | Request path. Path params use `:param`, for example `/users/:id`. |
| `tags` | no | string array | Searchable labels used by web preview and reports. |
| `version` | yes | integer | Endpoint spec version. |
| `env` | no | string array | Environments where this endpoint is valid. Missing means all configured environments. |
| `auth` | no | enum | `none`, `bearer`, `basic`, or `custom`. Missing uses project default. |
| `timeout` | no | integer | Request timeout in milliseconds. Missing uses project default. |
| `retry` | no | object | Retry policy. Missing uses project default. |
| `response.match` | no | enum | `shape` (default), `strict`, or `schema`. |
| `response.ignore` | no | string array | Strict-mode paths to ignore, for example `body.id` or `headers.x-request-id`. |

Unknown frontmatter keys are warnings unless a future compatibility mode promotes them to errors.

### Required body sections

Endpoint body sections must appear in this order:

1. `# <Sentence-case title>`
2. One-paragraph description
3. `## Request` with exactly one `http` code block
4. `## Expected response` with exactly one `http` code block
5. `## Error responses` with one or more `http` code blocks, optional reference examples
6. `## Assertions` with structured assertion rules, optional
7. `## Tests` with exactly one `agent-task` code block, optional but encouraged
8. `## Notes`, optional

Example:

````markdown
# Get user by id

Fetches a single user record by stable user identifier.

## Request

```http
GET {{baseUrl}}/users/:id
Authorization: Bearer {{authToken}}
Accept: application/json
```

## Expected response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": "{{id}}",
  "email": "user@example.com"
}
```

## Error responses

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "error": "not_found",
  "message": "User not found"
}
```

## Tests

```agent-task
- Verify the response status is 200.
- Verify response.body.id equals the requested id.
- Verify response.body.email is a valid email address.
```

## Notes

Use this endpoint after login or after creating a user in the onboarding pipeline.
````

### HTTP request block

The `## Request` section must contain exactly one fenced code block tagged `http`.

The first line is the request line:

```http
GET {{baseUrl}}/users/:id
```

Supported request-line forms:

```http
GET /users/:id
GET {{baseUrl}}/users/:id
POST https://api.example.com/users
```

Headers follow the request line as `Name: value` pairs. An empty line separates headers from the optional body.

```http
POST {{baseUrl}}/users
Authorization: Bearer {{authToken}}
Content-Type: application/json

{
  "email": "{{email}}",
  "name": "{{name}}"
}
```

If the URL is relative, MarkApiDown resolves it against the selected environment's `baseUrl`.

### Expected response block

The `## Expected response` section must contain exactly one fenced code block tagged `http`. Add `response.match` in frontmatter or use a fence suffix such as `http strict` for one-off strict matching.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": "usr_123",
  "email": "user@example.com"
}
```

Default `shape` mode compares:

- Status strictly.
- Headers as subset match. Expected headers must be present in the actual response, but extra response headers are allowed.
- Body as JSON shape when both expected and actual bodies are valid JSON. Otherwise, body is compared as an exact string.

`strict` mode requires the expected status, expected headers, and JSON/string body to match exactly, except documented ignored fields:

```yaml
response:
  match: strict
  ignore: [body.id, headers.x-request-id]
```

`schema` mode validates the actual response body against a JSON Schema block:

````markdown
## Schema

```json
{
  "type": "object",
  "required": ["id", "email"],
  "properties": {
    "id": { "type": "string" },
    "email": { "type": "string" }
  }
}
```
````

### Error responses section

The optional `## Error responses` section documents representative error contracts. It may contain one or more fenced `http` examples.

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "error": "not_found",
  "message": "User not found"
}
```

the current MarkApiDown release does not execute `## Error responses`; only `## Expected response` is compared during `mad exec`. Error responses are reference examples for humans, web source view, and AI agents.

### Assertions block

The optional `## Assertions` section contains structured rules evaluated after each execution. Results appear in CLI output and `mad_exec` MCP responses as `assertion_results`.

Each rule is a list item in the form `- <path>: <op> [value]`:

```markdown
## Assertions
- status: 201
- body.id: exists
- body.email: equals "ada@example.com"
- body.role: in [admin, user]
- headers.content-type: contains application/json
- body.slug: matches ^[a-z-]+$
```

Supported operators:

| Operator | Example | Description |
| --- | --- | --- |
| `exists` | `body.id: exists` | Field is present and non-null. No value operand. |
| `equals` | `status: 201` or `body.name: equals "Ada"` | Exact match. Bare value (no keyword) also means equals. |
| `contains` | `headers.content-type: contains application/json` | Substring match. |
| `in` | `body.role: in [admin, user]` | Value is one of a comma-separated list in brackets. |
| `matches` | `body.slug: matches ^[a-z-]+$` | Regex match. |

Path prefixes:

| Prefix | Example | What it checks |
| --- | --- | --- |
| `status` | `status: 200` | HTTP status code (numeric) |
| `body.<field>` | `body.id: exists` | JSON response body field, dot-separated |
| `headers.<name>` | `headers.content-type: contains json` | Response header, lowercase name |

A failing assertion is reported but does not change the exit code in the current release. Use structured assertions for machine-readable checks and `## Tests` for agent-executed validation.

### Tests block

The optional `## Tests` section contains one `agent-task` block. It gives AI agents and humans extra validation intent.

```agent-task
- Verify the created user can be fetched by id.
- Verify duplicate email returns 409.
- Do not log Authorization headers.
```

the current MarkApiDown release does not execute arbitrary code from `agent-task` blocks. Agents may use the tasks as instructions.

## Shared environment config

`api-docs/_shared/env.md` stores non-secret values per environment.

Example:

````markdown
# Environments

## dev

```yaml
baseUrl: http://localhost:8080
userId: 123
```

## staging

```yaml
baseUrl: https://staging.example.com
```

## prod

```yaml
baseUrl: https://api.example.com
```
````

Do not put secrets in `env.md`. Use `.env.local` for local secrets and OS environment variables for CI secrets.

## Variables

MarkApiDown uses `{{name}}` syntax in markdown content, request blocks, expected response blocks, pipeline definitions, and selected structured config values.

Path parameters use `:param` inside URL paths. A path parameter may be resolved from any variable source.

```http
GET {{baseUrl}}/users/:userId
Authorization: Bearer {{authToken}}
```

### Resolution priority

When the same variable is defined in multiple places, the highest-priority source wins:

1. Pipeline-level capture or inject.
2. CLI `--var key=value`.
3. Endpoint frontmatter.
4. `_shared/env.md` for the selected environment.
5. `.env.local`.
6. OS environment variables prefixed `MAD_`.

Example:

```bash
MAD_USER_ID=from-os mad exec api-docs/apis/users/get-user.md --var userId=from-cli
```

`{{userId}}` resolves to `from-cli` because CLI variables outrank OS environment variables.

### `.env.local`

`.env.local` uses dotenv syntax and must be gitignored.

```dotenv
authToken=local-development-token
webhookSecret=local-development-secret
```

`mad doctor` verifies that `.env.local` appears in `.gitignore`. If `.env.local` is missing from `.gitignore`, doctor reports an error with a suggested fix.

### OS environment variables

Only variables prefixed with `MAD_` are considered. The prefix is stripped and the remaining name is converted to lower camel case.

Examples:

| OS variable | MarkApiDown variable |
| --- | --- |
| `MAD_AUTH_TOKEN` | `authToken` |
| `MAD_BASE_URL` | `baseUrl` |
| `MAD_USER_ID` | `userId` |

### Missing variables

If a variable is referenced and not found, MarkApiDown returns a validation error before executing the request.

Error example:

```text
api-docs/apis/users/get-user.md: unresolved variable "authToken"
Fix: define authToken in .env.local, pass --var authToken=..., or set MAD_AUTH_TOKEN.
```

### Nested variables

Nested variables are not resolved recursively in the current release.

Invalid:

```yaml
apiHost: "{{host}}"
baseUrl: "https://{{apiHost}}"
```

If resolving `{{baseUrl}}` produces another unresolved `{{apiHost}}`, MarkApiDown returns an error instead of performing a second pass. This prevents surprising precedence behavior and secret leakage.

### Escaping variable syntax

To show literal `{{name}}` text in notes or examples, wrap it in an inline code span or a fenced code block that is not parsed for execution. Request and expected response blocks always treat `{{name}}` as a variable.

## Pipelines

A pipeline chains endpoint files and passes captured values between steps.

Pipeline files live in `api-docs/flows/`.

Example:

```markdown
---
type: pipeline
name: user-onboarding
description: Full onboarding flow
continue-on-error: false
parallel: false
---

# User onboarding

## Steps

1. **Create user** -> `apis/users/create-user.md`
   - Capture: `response.body.id` as `userId`
2. **Login** -> `apis/users/login.md`
   - Inject: `userId`
   - Capture: `response.body.token` as `authToken`
3. **Pair device** -> `apis/devices/pair-device.md`
   - Inject: `authToken`, `userId`
   - Assert: `response.status == 201`
```

### Pipeline frontmatter

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `type` | yes | string | Must be `pipeline`. |
| `name` | yes | string | Stable pipeline name. |
| `description` | no | string | Human-readable summary. |
| `continue-on-error` | no | boolean | Continue after a failed step. Default: `false`. |
| `parallel` | no | boolean | Run independent steps concurrently. Default: `false`. |

### Step syntax

Each ordered list item names a step and points to an endpoint file relative to `api-docs/`.

```markdown
1. **Create user** -> `apis/users/create-user.md`
```

Supported step directives:

```markdown
- Inject: `authToken`, `userId`
- Capture: `response.body.id` as `userId`
- Assert: `response.status == 201`
```

`Capture` uses JSONPath for JSON responses. Captured values have highest variable priority for later steps.

### Sequential and parallel behavior

Pipelines run sequentially by default. If a step fails and `continue-on-error` is false, MarkApiDown stops and reports the failing step.

When `parallel: true`, MarkApiDown may run steps concurrently only when their dependencies allow it. A step that injects a captured value waits for the step that captures it.

## Validation rules

MarkApiDown validates before execution.

### Missing frontmatter

Endpoint and pipeline files must start with frontmatter. A file whose first non-empty line is not `---` is invalid.

```text
api-docs/apis/users/get-user.md:1: missing frontmatter
Fix: add YAML frontmatter delimited by --- at the start of the file.
```

### Missing required fields

Required frontmatter fields must be present and have valid types. For endpoint files, missing `resource`, `protocol`, `method`, `path`, or `version` is an error.

### Section order

Endpoint sections must appear in canonical order. Optional sections may be omitted, but if present they must appear after required sections.

Invalid order:

```markdown
## Expected response

## Request
```

### Missing sections

Endpoint files must include `## Request` and `## Expected response`.

### Multiple HTTP blocks

`## Request` must contain exactly one `http` block. `## Expected response` must contain exactly one `http` block. Multiple `http` blocks in either section are an error because the engine would not know which one to execute or compare.

```text
api-docs/apis/users/get-user.md: multiple http blocks in ## Request
Fix: keep one executable request block and move alternatives to ## Notes using a non-http code fence.
```

### Invalid HTTP block

The request block must contain a valid request line. Headers must use `Name: value` syntax. Request bodies must follow a blank line after headers.

### Unsupported protocol

`protocol: ws` and `protocol: sse` are reserved for future versions. In the current release, validation may accept them for documentation, but execution returns an unsupported protocol error.

### Environment mismatch

If an endpoint declares `env: [dev, staging]` and the user runs `--env=prod`, MarkApiDown returns an invalid spec error with a suggested fix.

## Security rules

MarkApiDown treats markdown specs as safe-to-commit files. Secrets belong in `.env.local`, a secret manager, CI variables, or OS environment variables.

### Secret detection

The parser refuses secrets in versioned markdown sources such as `api-docs/_shared/env.md`, endpoint files, pipeline files, and `mad.md`.

Secret patterns include:

- Strings containing `Bearer eyJ`, commonly JWT-like bearer tokens.
- Hex strings longer than 32 characters.
- Values with prefixes `sk_` or `pk_live_`.

If a secret is found in `env.md`, MarkApiDown exits with code 5.

```text
api-docs/_shared/env.md:12: possible secret detected
Fix: move this value to .env.local or MAD_* environment variables.
```

### Allowed secret locations

`.env.local` may contain local secrets and must be listed in `.gitignore`.

CI should pass secrets through environment variables such as `MAD_AUTH_TOKEN`.

### Output masking

MarkApiDown masks auth values in CLI output, logs, reports, browser responses, and execution history.

Examples:

| Input | Output |
| --- | --- |
| `Authorization: Bearer abc123` | `Authorization: Bearer ****` |
| `Authorization: Basic dXNlcjpwYXNz` | `Authorization: Basic ****` |
| `authToken=abc123` | `authToken=****` |

### Production confirmation

Running against production requires confirmation in interactive mode.

```bash
mad exec api-docs/apis/users/delete-user.md --env=prod
```

MarkApiDown prompts before sending the request. Use `--yes` to skip confirmation in CI.

## Reports and exit codes

MarkApiDown commands use stable exit codes:

| Code | Meaning |
| --- | --- |
| 0 | Passed. |
| 1 | Test failed. |
| 2 | Invalid spec. |
| 3 | Engine error. |
| 4 | Network error. |
| 5 | Secret detected. |

Error messages include the file path when known, line number when applicable, and a suggested fix.

## Authoring conventions

Use sentence case for headings:

```markdown
# Create subscription
```

Avoid title case:

```markdown
# Create Subscription
```

Use stable, descriptive slugs:

| Method and path | Filename |
| --- | --- |
| `GET /users/:id` | `get-user-by-id.md` |
| `POST /orders` | `post-orders.md` |
| `DELETE /subscriptions/:id` | `delete-subscription-by-id.md` |

Do not overwrite existing endpoint files. Create a new version or update the existing file intentionally.

Do not inline secrets in request examples. Use variables.

## Migrating from Postman

MarkApiDown imports Postman collections into markdown endpoint files. The result should be reviewed by a human because Postman scripts can contain arbitrary JavaScript and environment behavior that does not map perfectly to markdown.

### Concept mapping

| Postman concept | MarkApiDown concept | Notes |
| --- | --- | --- |
| Collection | `api-docs/` project | Collection metadata becomes project prose and generated index content. |
| Folder | Resource folder | Folder names become resource directories such as `users/` or `orders/`. |
| Request | Endpoint markdown file | One request becomes one `<method>-<slug>.md` file. |
| Request URL | `path` frontmatter and `http` request block | `{{var}}` syntax is preserved. |
| Method | `method` frontmatter and request line | Methods are normalized to uppercase. |
| Headers | Headers in `http` request block | Authorization headers should use variables. |
| Body | Body in `http` request block | JSON bodies are formatted for readable diffs. |
| Tests | `## Expected response` and `agent-task` block | Simple status/body checks become expected responses. Complex JavaScript becomes manual review tasks. |
| Pre-request script | `agent-task` block | Imported as manual review instructions, not executable JavaScript. |
| Collection variables | `_shared/variables.md` or `_shared/env.md` | Non-secret values can be committed. Secrets must move to `.env.local`. |
| Environment | `_shared/env.md` section | Environment names map to markdown headings such as `## dev`. |
| Auth helper | Endpoint or project `auth` setting | Bearer/basic auth maps directly when possible. |
| Examples | `## Expected response` block | Postman examples become expected response candidates. |

### Migration workflow

1. Export the Postman collection as v2.1 JSON.
2. Export Postman environments separately if needed.
3. Run `mad import postman collection.json`.
4. Run `mad validate api-docs/`.
5. Move imported secrets to `.env.local` or `MAD_*` variables.
6. Run `mad index`.
7. Review imported `agent-task` blocks for manual follow-up.

### Known migration edge cases

Postman pre-request scripts are not executed by MarkApiDown. They are imported as human-readable tasks.

Dynamic Postman variables such as `{{$timestamp}}` require explicit MarkApiDown variables or pipeline captures.

Postman tests that depend on JavaScript side effects are imported as `agent-task` instructions.

Postman environments containing tokens are rejected by MarkApiDown if imported into `_shared/env.md`; move them to `.env.local`.
